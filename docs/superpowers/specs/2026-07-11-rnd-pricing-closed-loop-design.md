# 研发实验记录与核价闭环系统设计

## 1. 目标与范围

系统首要目标是让研发人员在手机或平板现场记录实验数据，内部测试通过后锁定版本，生成可追溯的核价 Excel，并让财务能够方便地接收、查看和下载文件。

主流程终点为财务确认接收核价文件。本阶段不包含采购询价、完整财务成本测算、生产工艺/BOM 下发，也不以飞书免登录作为验收条件。飞书相关字段与接口继续保留，后续作为外部身份绑定和消息通知能力接入。

## 2. 业务主线

```text
研发内勤录入需求
→ 研发总监审核
→ 研发总监分配任务
→ 研发人员接受任务
→ 研发人员记录配方、工序损耗和成品出成
→ 选择内部测试人员并提交
→ 测试人员完成品尝测试
→ 测试通过并锁定实验版本
→ 研发内勤生成核价文件
→ 研发内勤通知财务
→ 财务查看、下载并确认接收
```

测试不通过时，系统保留当前版本全部数据并自动建立下一版本，例如 A0 到 A1。停止打样时保存停止原因并进入停止项目池。

寄样与客户反馈作为可选支线，不再是生成核价文件的强制前置条件。测试通过后既可以直接生成核价，也可以先寄样再根据客户反馈决定通过、复打样或停止。

## 3. 状态模型

### 3.1 主流程状态

| 状态 | 说明 | 主要责任人 |
|---|---|---|
| `DRAFT` | 需求草稿 | 研发内勤 |
| `PENDING_REVIEW` | 待审核 | 研发总监 |
| `PENDING_ASSIGNMENT` | 待分配研发 | 研发总监 |
| `PENDING_ACCEPTANCE` | 待研发接受 | 被分配研发人员 |
| `SAMPLING` | 打样及实验记录中 | 研发人员 |
| `PENDING_TEST` | 待内部测试 | 测试人员 |
| `TEST_FAILED` | 测试不通过，待复打样 | 研发人员 |
| `VERSION_LOCKED` | 测试通过，实验版本只读 | 系统 |
| `PRICING_PENDING` | 可生成核价文件 | 研发内勤 |
| `PRICING_GENERATED` | 核价文件已生成 | 研发内勤 |
| `FINANCE_NOTIFIED` | 已通知财务 | 财务 |
| `FINANCE_RECEIVED` | 财务已确认接收 | 财务 |
| `COMPLETED` | 本轮闭环完成 | 系统 |
| `STOPPED` | 已停止 | 研发总监确认 |

所有状态变化必须通过后端状态机，不允许前端直接指定最终状态。重复提交必须具备幂等保护，避免重复版本、重复测试任务、重复核价文件或重复财务通知。

### 3.2 寄样支线状态

| 状态 | 说明 |
|---|---|
| `NOT_REQUIRED` | 本版本无需寄样 |
| `PENDING_SHIPMENT` | 待登记寄样 |
| `SHIPPED` | 已寄样，待反馈 |
| `FEEDBACK_PASSED` | 客户反馈通过 |
| `FEEDBACK_RESAMPLE` | 客户要求复打样 |
| `FEEDBACK_STOPPED` | 客户或业务决定停止 |

寄样状态独立于实验版本和核价状态。客户要求复打样时触发下一样品版本。

## 4. 角色与权限

| 角色 | 核心职责 | 数据范围 |
|---|---|---|
| 研发内勤 `RND_ASSISTANT` | 录入需求、查看进度、寄样反馈、生成核价、通知财务 | 全部需求及后续业务资料，不可审核和分配 |
| 研发总监 `RND_DIRECTOR` | 审核、分配、停止确认、全局监督，可兼任研发 | 全部研发项目 |
| 研发人员 `RND_ENGINEER` | 接受任务、填写实验单、提交内部测试 | 仅本人负责的可操作任务，历史资料只读 |
| 测试人员 `TESTER` | 完成内部品尝测试，选择通过或复打样 | 分配给本人的测试任务 |
| 财务 `FINANCE` | 查看、下载核价文件并确认接收 | 已通知财务的核价文件及历史已接收文件 |
| 管理员 `ADMIN` | 账号、角色、字典、模板和流程配置 | 全部配置与审计数据 |

权限由后端作为唯一事实来源。登录会话返回菜单、路由、按钮和数据范围权限，PC 与手机端只消费权限结果，不再分别维护独立角色矩阵。后端必须再次校验角色、业务状态、任务负责人和版本锁定状态。

## 5. 终端职责

### 5.1 手机端

手机端用于日常业务和现场操作，底部只保留三个入口：`待办`、`样品`、`我的`。

待办按角色自动展示：

- 研发内勤：录入需求、待寄样、待生成核价、待通知财务。
- 研发总监：待审核、待分配、异常/超期待办、本人研发任务。
- 研发人员：待接受、打样中、测试退回复打样。
- 测试人员：待品尝测试。
- 财务：待接收核价文件。

每张待办卡只提供一个主动作，动作完成后返回待办并刷新数据。所有加载页面需要有加载中、空状态、失败提示和重试按钮。

### 5.2 PC 管理端

PC 端用于批量管理、复杂查询、历史归档、模板配置和报表导出：

- 工作台：按角色展示进度、异常和待办数量。
- 样品需求：录入、审核、查询和需求详情。
- 研发任务：任务池、任务分配、实验记录和历史版本。
- 测试记录：内部测试列表、详情和导出。
- 寄样与核价：可选寄样支线、核价生成、通知财务。
- 财务核价收件箱：待接收、已接收和全部文件。
- 文件归档：按样品、版本、类型和时间查询。
- 系统设置：账号权限、物料字典、表单字段、流程和 Excel 模板。

## 6. 实验单设计

实验单只保留完成研发记录所需的数据，减少现场填写量。

### 6.1 基本信息

产品名称、规格、样品编号、样品版本、研发负责人、实验日期和实验摘要。能由需求或任务继承的字段自动带入且不可重复填写。

### 6.2 配方

每行包含：类别、是否主原料、ERP 物料编码、物料名称、重量、单位、自动比例、利用率和备注。

- 类别为原料、辅料或包材。
- 利用率默认 100%。
- 比例由系统根据重量自动计算。
- 包材不参与主原料和成品得率计算。
- 只允许选择一个主原料。
- 物料字典后续通过 ERP API 同步，研发人员可调整并确认当前实验数据。

### 6.3 工序损耗

支持两种模式：

- 快速打样：直接采用推荐工序，逐步填写。
- 编排后打样：先调整工序名称、顺序和控制要点，再逐步填写。

每道工序记录工序名称、投入重量、产出重量、余料重量、余料去向、自动损耗重量、自动损耗率和备注。工序可新增、复制、删除和移动；已锁定版本不可修改。

### 6.4 成品出成

记录成品实际产出重量，系统按下式计算：

```text
成品得率 = 成品实际产出重量 ÷ 主原料实际投入重量 × 100%
```

草稿允许不完整保存；提交测试前必须校验主原料、主原料重量、成品产出和至少一个有效工序。

## 7. 测试与版本锁定

研发提交时必须选择测试人员。测试单记录测试人员、测试时间、外观、气味、口味、口感、复热表现、综合意见和结论。

- 测试通过：实验单、配方、工序、附件和测试记录全部锁定，只读归档。
- 测试不通过：当前版本锁定为失败历史，复制必要基础数据生成下一版本草稿。
- 停止：保存停止原因、提出人和确认人。

历史版本按 A0、A1、A2、A3 递增，每个版本可以查看实验单、测试记录、附件、寄样和核价文件。

## 8. 核价文件与财务收件箱

核价文件只能使用已锁定实验版本的数据生成，包括产品信息、样品版本、原辅料与包材、实际重量、比例、利用率、参考领料重量、主原料投入、成品产出、得率、研发负责人和生成时间。

文件版本规则为 `A0-核价V1`、`A0-核价V2`、`A1-核价V1`。每次生成创建独立文件与归档记录，禁止覆盖历史文件。

财务手机端和 PC 端均提供核价收件箱：

- 待接收：状态为 `FINANCE_NOTIFIED`。
- 已接收：状态为 `FINANCE_RECEIVED`。
- 全部：以上状态的全部历史。

财务可查看产品、样品编号、样品版本、核价版本、研发负责人、通知时间，下载 Excel，并点击确认接收。财务不修改研发实验数据。

## 9. 数据与服务边界

PostgreSQL/H2 测试数据库是业务数据唯一事实来源。`SampleWorkflowService` 中的内存 Map 不再承担主业务存储；缓存仅允许用于可重建的查询加速。

后端按业务边界拆分：

- `SampleRequestService`：需求录入与审核。
- `RndTaskService`：任务池、分配与接受。
- `ExperimentService`：实验草稿、配方、工序、附件和版本锁定。
- `InternalTestService`：测试任务与结论。
- `PricingWorkflowService`：核价生成、通知、财务接收和下载。
- `ShipmentService`：可选寄样支线。
- `ArchiveService`：统一归档与下载。
- `PermissionService`：角色、动作与数据范围判定。

文件首版继续存本地归档目录，通过存储接口隔离，后续可替换 MinIO/NAS。

## 10. 错误处理与审计

所有业务错误返回稳定错误码和中文提示。手机端不得只结束 loading；必须展示错误原因和重试入口。保存、提交、审核、锁版、复打样、生成核价、通知财务、下载和确认接收都写入审计日志。

高风险动作具备以下保护：

- 保存草稿可重复执行，更新当前草稿。
- 提交测试只能成功一次。
- 测试结论只能提交一次。
- 同一次生成操作不能因双击产生重复文件。
- 财务确认接收可安全重试。

## 11. 测试与验收

### 11.1 自动化测试

- 后端单元测试：状态机、权限、版本递增、实验计算、核价生成和幂等。
- 后端集成测试：数据库重启恢复、文件归档、跨服务事务。
- 前端组件测试：角色待办、错误状态、表单校验和下载动作。
- Playwright PC 流程：五个角色接力完成一个样品。
- Playwright 手机流程：五个角色接力完成一个样品。

### 11.2 必须通过的主验收场景

```text
内勤登录并录入需求
→ 总监审核并分配
→ 研发接受任务并保存实验单
→ 研发提交测试
→ 测试人员通过
→ 内勤生成核价并通知财务
→ 财务在待接收列表看到文件
→ 财务成功下载 Excel
→ 财务确认接收
```

补充场景包括测试失败生成 A1、锁版后禁止修改、无权限访问返回 403、重复点击不生成重复数据、服务重启后历史数据仍可查询。

## 12. 实施优先级

1. 建立跨角色端到端主流程测试，固定当前失败点。
2. 修复财务端核价状态读取和下载流程。
3. 解耦寄样与核价，测试通过即可生成核价。
4. 统一手机端角色待办和明确下一步动作。
5. 完善实验单保存、提交、锁版和复打样版本。
6. 增加财务确认接收状态与审计。
7. 收敛后端权限并移除前端重复角色矩阵。
8. 将业务读取完全迁移到数据库，清理双数据源。
9. 完整执行 PC、手机、权限、导出和重启恢复测试。

## 13. 非目标

- 不实现采购询价和供应商管理。
- 不实现财务完整成本拆解与正式报价审批。
- 不生成生产工艺文件或生产 BOM。
- 不以飞书登录、事件回调和消息卡片作为本阶段上线条件。
- 不在本轮替换现有 Vue 3、Spring Boot 3、JPA、Flyway 和 Apache POI 技术栈。
