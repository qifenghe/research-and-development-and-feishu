4. 虚拟机网络和 SSH 配置过程

4.1 故障和处理依据

初始 eth0 为 DOWN，没有 IPv4、没有路由，/etc/netplan 没有 YAML 文件。启用网卡后出现 UP、LOWER_UP，说明链路已接通。尝试 DHCP 后没有分配到 IPv4。Windows 实际查询确认使用自建内部 NAT，因此改用固定 IP。

Windows 管理员 PowerShell 查询命令：

Get-VMSwitch -Name "Longhui-NAT"
Get-NetNat
Get-NetIPAddress -InterfaceAlias "vEthernet (Longhui-NAT)" -AddressFamily IPv4

这些是查询命令。重建宿主 NAT 前必须检查其他虚拟机和现有 NAT，不能直接重复创建或删除现有网络。

4.2 Ubuntu 固定 IP

文件：/etc/netplan/01-eth0.yaml。以下为已使用的内容：

network:
  version: 2
  renderer: networkd
  ethernets:
    eth0:
      dhcp4: false
      addresses:
        - 10.77.0.10/24
      routes:
        - to: default
          via: 10.77.0.1
      nameservers:
        addresses: [223.5.5.5, 119.29.29.29]

在虚拟机控制台应用，防止 SSH 因网络变更中断后无法恢复：

sudo chmod 600 /etc/netplan/01-eth0.yaml
sudo netplan generate
sudo netplan apply
ip -br addr show eth0
ip route
ping -c 3 223.5.5.5
getent hosts ubuntu.com

新建其他虚拟机时，必须确认 10.77.0.10 未被占用。fe80:: 地址并不表示已经获得可用 IPv4。网关不响应 ping 不一定代表 NAT 失效；本次网关不回 ping，但外网地址可以 ping 通。

4.3 SSH

sudo apt update
sudo apt install -y openssh-server
sudo systemctl enable --now ssh

Windows 宿主机执行前述 ssh 命令连接。SSH 主机指纹发生变化时，应核对是否重建了虚拟机，不能机械忽略告警。Ubuntu 登录密码与系统网页管理员密码是两套密码。

5. Docker 安装和镜像准备

5.1 安装方式

Ubuntu 安装 Docker Engine 和 Compose 插件，不在 Ubuntu 单独安装 Java、Nginx 或 PostgreSQL 服务。这些运行环境在容器内。

以下是本次 Ubuntu 24.04 amd64 使用的安装过程；其他发行版或架构应查官方文档调整：

sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
sudo tee /etc/apt/sources.list.d/docker.sources > /dev/null <<'EOF'
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: noble
Components: stable
Architectures: amd64
Signed-By: /etc/apt/keyrings/docker.asc
EOF
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
sudo docker version
sudo docker compose version

参考：https://docs.docker.com/engine/install/ubuntu/

6. 部署包、源码和版本依据

基础代码为 main 提交 9af994e。本次交付是在该版本上增加生产部署修正，不等于该提交本身已经包含全部修正。原主工作目录还有更早分支及未提交修改，不要直接从任意工作目录重新打包覆盖生产。

本次生产修正包括：

  • 关闭测试账号补建：关闭启动初始化时，登录回退逻辑也不能补建默认账号。
  • 电脑端和手机端登录页不再默认填写测试口令或显示测试账号快捷入口。
  • 新增 V15_1 权限 ID 扩容迁移，以及 V45 现有库扩容迁移；不修改已存在的迁移文件校验和。
  • PostgreSQL 初始化时建立 clob=text 兼容域，支持历史迁移中的 CLOB 写法。
  • Flyway 首次初始化设为 baselineOnMigrate=true、baselineVersion=0，从 V1 完整执行迁移。

7.2 本次现场增加的 Flyway 补充配置

本次旧包在首次启动时，因预建兼容类型导致 Flyway 判断 public 非空，却没有 schema history。最终采用以下文件修复：/opt/longhui/compose.override.yaml。

sudo tee /opt/longhui/compose.override.yaml > /dev/null <<'EOF'
services:
  backend:
    environment:
      SPRING_FLYWAY_BASELINE_ON_MIGRATE: "true"
      SPRING_FLYWAY_BASELINE_VERSION: "0"
EOF

Docker Compose 默认加载 compose.yaml 和 compose.override.yaml。本机 r1 包已把这两个参数写入基础配置，新安装无需另建相同 override；现场已有 override 应一并保存和交接。

版本必须为 0。采用默认 1 会跳过 V1，导致缺表。此设置是本次新建数据库兼容预置类型的处理方式，不应未经核对套用于来源不明、已有业务表但无迁移历史的数据库。

7.3 验证和启动

cd /opt/longhui
sudo docker compose config -q
sudo bash /opt/longhui/deploy.sh

config -q 没有输出且退出状态为 0，表示配置解析通过。有报错应先停止，不要反复重跑部署。

脚本执行的内容：

  1. 如没有 .env，则生成数据库密码、会话密钥和管理员初始密码；已有 .env 不覆盖。
  2. 导入 images.tar 或 images.tar.gz 中的 amd64 镜像。
  3. 创建持久卷，将附件目录属主设为 10001:10001。
  4. 启动数据库、后端和网页服务，数据库有就绪检查。
  5. 轮询本机 18080 健康接口；最多 90 次，每次间隔 2 秒，连接等待也会增加总耗时。
  6. 创建 admin 管理员；同名管理员已存在时不改密码。
  7. 检查电脑端、手机端页面。
  8. 启用 Docker 开机启动，以及每日备份 timer。

脚本健康检查写死了 18080 和网页 80。今后如调整 Compose 的 HTTP_PORT 或 BACKEND_CHECK_PORT，必须同步修改脚本检查地址。

9. 日常维护和排障命令

以下命令均在 Ubuntu 执行。先进入 /opt/longhui。任何完整 Compose 渲染结果和 inspect 环境变量可能包含密码，分享前必须脱敏。

cd /opt/longhui
sudo docker compose ps -a
sudo docker compose logs --tail=100 backend
sudo docker compose logs --tail=100 web
sudo docker compose logs --tail=100 db
curl -fsS --max-time 10 http://127.0.0.1:18080/actuator/health
curl -I --max-time 10 http://127.0.0.1/admin/login
df -h
sudo docker system df

预期健康接口为 {"status":"UP"}，登录页面 HTTP 200。容器 Started 只代表进程已启动，不代表应用初始化成功。

按需重启单个服务：

sudo docker compose restart backend
sudo docker compose restart web

临时停止或恢复整套服务（会中断用户访问）：

sudo docker compose stop
sudo docker compose start

数据卷信息查询：

sudo docker volume inspect longhui-rnd_postgres_data
sudo docker volume inspect longhui-rnd_archive_data

禁止日常维护使用 docker compose down -v、docker volume prune 或未经核对的 docker system prune --volumes。它们可能删除业务数据。

日志超过一屏时：

sudo docker logs --tail=100 longhui-rnd-backend-1 2>&1 | less

less 中 Shift+G 到底部，Page Up/Page Down 翻页，q 退出。Ctrl+C 终止当前前台等待或跟踪，不等于删除容器。Hyper-V 文字控制台不宜依赖鼠标滚动；优先 SSH。输入不显示时可尝试 stty sane、reset，或重新建立 SSH 会话。

无法登录使用系统账号密码，不是 Ubuntu 密码；查账号状态和后端日志，不要清库
修改 .env 后数据库鉴权失败已有数据库卷不会因 .env 改变而自动修改数据库角色密码，需要协调修改

10. 管理员、员工账号和密钥

只在管理员终端查看初始口令：

sudo cat /opt/longhui/credentials.txt

通过系统账号管理创建员工并分配角色。不要继续使用开发环境的默认测试账号和 123456。生成口令是否已修改、员工账号是否已建立，均需要现场负责人确认。

init-admin.py 仅新增缺失的 admin，不会重置已有密码。忘记密码时应使用已验证的账号管理或管理员恢复流程；本手册没有提供通用重置脚本，不能通过删除 .env 或重新解压来重置。

.env、credentials.txt、备份和花生壳账号均由指定维护负责人保管。文档不写真实口令、飞书密钥或花生壳订阅信息。应用数据库口令、会话签名密钥、Ubuntu 密码、Windows 管理员密码互相独立。

11. 备份、恢复和重启验证

11.1 当前备份机制

deploy.sh 安装两个 systemd 单元：longhui-backup.service、longhui-backup.timer。计划每天北京时间 03:00 运行，Persistent=true 可能在错过时间后补跑。脚本使用日期命名文件时采用宿主机时区，因此文件名时间不一定与北京时间相同。

sudo systemctl list-timers --all longhui-backup.timer
sudo systemctl status longhui-backup.timer --no-pager
sudo journalctl -u longhui-backup.service -n 80 --no-pager

备份内容：数据库 pg_dump 自定义格式、附件归档、.env、credentials.txt。脚本为保证数据与附件的一致性，会短暂停止后端；执行结束或失败退出时会尝试重新启动后端。并发备份尚未实现文件锁，不要在自动任务执行时又手动运行。

手动触发：

cd /opt/longhui
sudo bash backup.sh
sudo ls -lh backups

脚本按修改时间清理超过 14 天的匹配备份，实际数量不保证恰好 14 份。备份失败、磁盘满、系统时钟变化都需另行监控。

必须由维护人员检查新备份是否存在、大小是否合理、后端是否重新健康，并将备份复制到独立磁盘或 NAS。本机备份不能防止宿主机或虚拟磁盘损坏。备份内含敏感配置，应限制权限并按公司要求加密保存。

11.2 恢复流程（尚未在公司服务器演练）

恢复会覆盖目标库和目标附件。优先在独立测试项目/虚拟机恢复，禁止直接在有新业务数据的生产卷上试验。正式恢复前确认目标时间点、停机窗口、回退备份及负责人。

  1. 保留当前生产备份、镜像版本、compose 和 override。不要在运行中的数据库目录直接覆盖文件。
  2. 将选定备份解压至仅管理员可读的临时目录，确认含 database.dump、archive.tar.gz、.env、credentials.txt。
  3. 使用对应应用镜像、相同 PostgreSQL 主版本和配置准备目标环境；新数据卷初始化前使用备份对应的数据库口令。
  4. 停止目标 web、backend，保留 db 运行；确认不会有用户写入。
  5. 通过 PostgreSQL 的 pg_restore 恢复 database.dump。下面为命令模板，RESTORE_DIR 必须替换为已确认的备份解压目录：
# 模板：在确认好的恢复目标环境中执行，不能直接在未知生产环境照抄。
sudo docker compose exec -T db pg_restore --clean --if-exists --no-owner --exit-on-error -U rnd_sample -d rnd_sample < "$RESTORE_DIR/database.dump"
  1. 在已确认的 archive_data 目标卷内清理旧归档再恢复 archive.tar.gz；只做覆盖解压会残留已被备份删除的文件。此步骤有删除风险，应由维护人员核对卷名和备份后执行。
  2. 将目标附件属主恢复为 10001:10001。保留/恢复配套会话密钥；若变更签名密钥，用户需要重新登录。
  3. 确保 .env 的数据库口令与实际 PostgreSQL 角色一致。已有数据卷不能靠更换 .env 自动同步口令。
  4. 启动 backend、web；核对健康、登录、物料数量、抽样配方、核价记录和附件可读性。
  5. 记录恢复耗时、备份时间点和数据核对结果，再恢复员工访问。

上述是恢复运行手册，不代表恢复脚本或演练已经完成。后续应在隔离环境验证并补充可重复的恢复脚本。

11.3 虚拟机重启验收

Docker 已启用开机启动，三个服务设置 restart: unless-stopped；若维护人员主动 stop，重启后的行为不能仅凭策略推断。Hyper-V 虚拟机自动启动策略和 Windows 花生壳是否能在无人登录时自动上线，都需现场核实。

在停机窗口执行重启后，检查：SSH 可用、Compose 服务健康、内网网页登录、花生壳在线、公网访问和飞书入口。当前没有这套端到端重启验收记录。

12. 更新、回退和后续 CI/CD

12.1 手工更新原则

deploy.sh 是首次交付安装脚本，不能把反复执行它当作长期版本发布：旧目录中的 images.tar 会重新装载 20261019 镜像，可能把程序降回旧版本。

更新前应：

  1. 确认源码已包含本次所有生产修正，并固定版本号/提交号。
  2. 在构建环境运行后端测试、前端类型检查与构建，以及真实 PostgreSQL 首次初始化和升级测试。
  3. 准备新的 linux/amd64 后端镜像和匹配的两套前端资源；使用独立版本标签并记录摘要，不覆盖旧标签。
  4. 在临时发布目录验证新包及校验和；不直接解压覆盖 /opt/longhui。
  5. 备份生产数据库、附件、.env、credentials.txt、compose、override、nginx 和原前端文件；当前 backup.sh 不包含全部应用配置，配置备份需额外完成。
  6. 根据发布说明审查数据库迁移与兼容性；维护窗口内导入新镜像、更新镜像标签及前端目录，保留原目录供回退。
  7. 不替换生产密钥，不更改 Compose 项目名和数据卷指向，不顺带升级 PostgreSQL 主版本。
  8. 配置检查通过后用 docker compose up -d --no-build --pull never 应用变更；必要时重启 web 使挂载文件与上游解析刷新。
  9. 进行健康、登录、角色、上传导出和关键业务抽查，记录版本与结果。

程序回退和数据库回退是两回事。数据库迁移通常不会因换回旧镜像自动撤销。只有确认新数据库结构与旧程序兼容时，才能直接换回旧镜像；否则需要按审定恢复方案处理，并明确恢复会丢失哪些新写入数据。

12.2 CI/CD 目标（未实施）

私有代码仓库 → 自动测试 → 构建 amd64 后端和前端/Nginx 镜像 → 国内私有镜像仓库 → 公司服务器备份并发布 → 健康及业务检查。

先实行自动构建、手动确认发布，稳定后再评估自动发布。国内仓库和 CI 平台账号、网络可达性、发布凭据及流水线均尚未配置。release.sh 仅曾作为方案中的命令示例，不是当前已交付文件。

首先把交付目录中的生产 patch、Compose、初始化和维护脚本纳入正式仓库，增加全新 PostgreSQL 迁移验收，避免再次出现仅 H2 测试通过、实际部署失败。发布流量由服务器主动拉取或内部受控 runner 执行，不需为了 CI/CD 把 SSH 映射公网。
